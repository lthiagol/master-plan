# M241 Review cycle 1 findings

- F-01 (medium, spec-drift): AC-05 / scope "one row per queued milestone (id, lifecycle, **cycle count**, lifecycle-position bar)" requires a real cycle count on the takeover row, but the implementation hard-codes `cycle: 1` in `TakeoverRow`. The underlying `QueueRow` (`crates/raul/src/tui/autopilot.rs:1515`) does not carry a cycle field, and `queued_milestones` (`crates/raul/src/tui/autopilot/setup.rs:626-655`) maps the queue view onto `TakeoverRow` with `cycle: 1` and `cycle: 1` in the fallback path — the runner's own code comment is honest: "the typed queue carries no cycle count; the drive has not reported one until the first refresh lands, so render 1 rather than a misleading 0." The data is in fact available: `DetailPanel::from_session_show` (`crates/raul/src/tui/autopilot.rs:2005-2026`) reads `session.queue_cycle_history[].cycle`, and `session.cycle_cap` is read at line 2033-2038. A real fix is to add a `cycle: Option<u64>` field to `QueueRow`, populate it in `QueueView::from_session_show`, and render the actual value (or omit the chip) in the takeover row. The runner flagged this honestly in note 4(c) of the cycle-1 dispatch and chose to ship 1 rather than extend the data model — a fair scope call given the L-effort budget, but the spec lists cycle count as a required row component, not as a fallback. Test `each_row_carries_id_lifecycle_cycle_and_position_bar` (`crates/raul/tests/autopilot_while_executing.rs:116`) only asserts `cycle >= 1`, which is the bare minimum that 1 satisfies; it does not pin the spec's intent. Net: the takeover will show "cycle 1" for every queued milestone regardless of the actual state, which is a real spec gap. MEDIUM, not HIGH, because the runner has been transparent and the value is functionally a placeholder rather than a wrong value; not LOW because the spec explicitly names the field and the data is reachable.
