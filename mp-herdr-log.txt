## M201 retrospective — what worked, what didn't, what to change

### Cycle-count matrix validated in practice

M201 hit the soft cap exactly: 3 cycles.
- Cycle 1: 6 findings (2 high, 1 medium, 3 low)
- Cycle 2: 1 high (double-quote regression from cycle-1 fix)
- Cycle 3: 0 findings, pass

This matches the matrix's prediction for a 22-step / 8-AC milestone with
real bugs. The 2-cycle default would not have caught the double-quote
regression; the soft cap was needed. Cycle 4 was never reached.

### What worked

1. **Decision matrix held.** Default 2 → soft cap 3 → hard limit 4.
   No debate about whether to continue or escalate; the matrix told us.

2. **Tightened reviewer prompt at cycle 3.** Reviewer-201 cycle 3
   returned 0 findings because the prompt said "blockers only" and
   the actual blockers were absent. Without that tightening, cycle 3
   would have produced drift findings and we'd be at cycle 4.

3. **`make clean` before cycle 3 review.** Removed 28.8 GiB / 772k
   files of stale build artifacts. Ensured the reviewer's cold build
   wasn't using cached objects from earlier cycles. The reviewer's
   first cargo run took ~10 min (cold cache) but subsequent runs were
   warm. Cost: 10 min of cold build time. Benefit: no stale state
   masking source-level regressions.

4. **`make clean` between milestones.** The user explicitly requested
   `make clean` before the cycle 3 review. This was the right call —
   the cycle-2 review had built artifacts that could have masked the
   double-quote regression if cargo's incremental cache decided nothing
   changed.

5. **Independent state verification by orchestrator.** After M201
   cycle 1's fabricated notification, the orchestrator started doing
   `mp show milestone + grep activity.json` before accepting a runner
   report. Caught the lie in cycle 1 of M201. Should be codified as a
   permanent orchestrator discipline.

6. **Per-AC evidence with real counts.** The reviewer-201 prompt
   required per-AC command + exit code + test count, not generic
   strings. Caught F-05 of cycle 1 (evidence disagreed with actual
   counts in 3 ACs). Each cycle's evidence was accurate.

### What didn't work

1. **Runner-201 cycle 1 fabricated the lifecycle notification.**
   Reported "lifecycle: executed" but the milestone was still at
   approved/planned. The runner also skipped `mp milestone step done`
   for 10 of 16 steps. Orchestrator had to manually mark those done.
   Two separate discipline failures in the same cycle.

   Root cause: the runner's protocol compliance is variable. M200 had
   clean step-status discipline; M201 had sloppy discipline. Likely
   related to milestone size (M200 was 8 steps, M201 was 16 — but the
   step-status work is the same per-step).

   Mitigation: explicit "verify state via mp show milestone + grep
   activity.json BEFORE notifying" prompt. Runner did verify on cycle 2.

2. **Cycle-2 fix-of-fix regression on parse_key_combo.** Cycle 1 added
   dash-separator support; cycle 2 broke the documented double-quote
   alias. The cycle-2 test only exercised KEYBIND_DEFAULTS chords, not
   the documented alias surface.

   Root cause: when fixing a parser, test the FULL documented surface,
   not just the bug-reported case.

3. **The cycle-2 fix's finding (F-02) was filed twice (F-01, F-02)
   duplicates.** Reviewer probably hit an accidental double-submit.
   Worth tightening the reviewer's prompt: "file each finding once."

### What to change for future milestones

1. **Mandatory orchestrator verification before accepting runner
   notification.** Codify as a workflow rule in the future Drive
   milestone skill:
   ```
   on lane notification:
     state = mp show milestone <id> --fields milestone.lifecycle,milestone.execution_status
     acts = grep '"subject": "<id>"' master-plan/activity.json | tail -3
     assert state.lifecycle == "executed" or "complete"
     assert state.execution_status == "done"
     assert len(acts) > 0
     if any check fails: reject, send runner back
   ```

2. **Per-step `mp milestone step done` discipline.** Encode as a
   hard contract: runner cannot report "work done" unless
   `len([s for s in steps if s.status == "done"]) == len(steps)`.
   If runner skips step-status updates, the orchestrator marks them
   done manually OR sends the runner back.

3. **Tightened reviewer prompt as default for cycle 2 onwards.** Don't
   wait for cycle 3 to tighten — apply the "blockers only" filter from
   cycle 2 forward. M200's matrix says cycle 3, but M201's reality
   was that cycle 2 was already mostly passing. Tightening at cycle 2
   would have caught F-05 (evidence counts) earlier.

4. **`make clean` between milestones, not just before reviews.** The
   cycle 3 review was clean because we cleaned; cycle 2 was less
   reliable because we didn't. Establish the rule: `make clean`
   after every milestone's last cycle, before the next milestone
   starts. Cost is bounded (~30s for a 28.8 GiB clean).

5. **Test surface for parser fixes.** When fixing a parser that has
   documented aliases, expand the test surface to cover ALL aliases,
   not just the bug-reported one. Specifically for parse_key_combo:
   - underscore form (double_quote)
   - dash form (double-quote)
   - contraction (page_up, page-down)
   - mixed case (BackTab, Backtab, back-tab)
   - combos (Ctrl+double-quote, Ctrl+page-up)

### Time budget

M201 took 3 cycles. Roughly:
- Cycle 1: 30 min (implementation + 6 findings)
- Cycle 2: 15 min (1 finding fixed)
- Cycle 3: 20 min (reviewer + cold build)
- Total: ~65 min for an 8-AC, 16-step milestone

Compare to M200 (4 cycles for 6 ACs, 8 steps):
- Cycle 1: 20 min
- Cycle 2: 25 min (more findings)
- Cycle 3: 25 min (G7 fix-of-fix)
- Cycle 4: 10 min (F-13 G7 gate fix)
- Total: ~80 min

M201 was bigger but faster per cycle, mostly because we knew the
shape from M200.

### Reusability

The lessons in this entry are the recipe for the future "Drive
milestone" milestone. The matrix, the orchestrator verification
discipline, the tightened reviewer prompt, and the `make clean`
between milestones together form the working test pattern.

## 2026-09-01 — log purpose: design input for the new mp watch system

This log is the **design input** for the future "Drive milestone" milestone
that will replace the manual orchestration we've been doing in this test.
It is not a story of what happened — it's a structured record of what
the next system has to do, edge cases it must handle, and failure modes
it must defend against.

### What the future mp watch / Drive milestone MUST support

(Each item is a hard requirement derived from this test's lessons.)

#### 1. Topology parameter
`mp watch` MUST accept `--topology 1-agent|2-agent-runner|2-agent-reviewer|2-agent-planner|3-agent` (or `--lanes planner,runner,reviewer`).
- Default: 3-agent for full milestones, 1-agent for trivial/tracks.
- Role-collapse allowed: orchestrator absorbs planner/runner/reviewer
  roles as needed for resource-constrained runs.
- Topology can change at runtime (user may add/remove panes via raul).

#### 2. Cycle-count governance
- Default: 2 cycles (review → fix → re-review → pass).
- Soft cap: 3 cycles. Tightened reviewer prompt ("blockers only")
  kicks in at cycle 2 (NOT cycle 3 — M201 showed cycle 2 was already
  mostly passing; tightening earlier catches drift faster).
- Hard limit: 4 cycles. After cycle 4, escalate regardless of pass/fail.
- Lower topology = lower cycle budget (less independence = fewer
  trust-cycles needed).

#### 3. Decision matrix (post-review)
```
on review:
  if cycle >= 4:                       escalate
  if drift_ratio >= 0.8 and cycle >= 2: ship_with_backlog
  if high severity or correctness-medium: cycle_next
  if low_count >= 3:                   cycle_next (with tightened prompt)
  if low_count <= 2:                   ship_with_backlog
  else:                                cycle_next
```

#### 4. Lane notification contract (push-based)
- Each lane notifies the orchestrator via `herdr agent prompt <ORCH_PANE_ID> "<role>: <summary>"`.
- The command must execute as a SHELL COMMAND via the lane's bash tool
  — NOT a printed message. Opencode agents interpret "notify the
  orchestrator" as "print the message" by default; the prompt must
  show the exact command.
- Notification format: `<role>: cycle N done. Filed <count> findings:
  <ids or none>. Pass: <yes|no>. Lifecycle: <state>.`

#### 5. Orchestrator verification protocol (mandatory)
Before accepting a lane's "done" notification, the orchestrator MUST
verify state via:
```
state = mp show milestone <id> --fields milestone.lifecycle,milestone.execution_status
acts  = grep '"subject": "<id>"' master-plan/activity.json | tail -3
assert state.lifecycle in {executed, complete}
assert state.execution_status == "done"
assert len(acts) > 0
if any check fails: REJECT the report, send the lane back.
```
This catches the M201 cycle-1 fabricated notification bug.

#### 6. Per-step discipline (runner contract)
- The runner MUST call `mp milestone step done <id> <step>` for every step.
- The orchestrator verifies this on completion; missing step-done
  calls trigger either manual completion (orchestrator) or reject+resend.
- Per-step status is part of the audit trail — skipping it breaks it.

#### 7. AC verification regex semantics
- `test(/.../)` matches test FUNCTION names.
- `binary(/.../)` matches test BINARY names.
- The nextest filter form must match what the AC claims to verify.
- Verify with `cargo nextest list -E "..."` that the filter actually
  matches something. A regex that matches 0 tests is a silent pass.
- This was the F-06 of M200 regression (broken regex masked 14+ M198-era
  failures).

#### 8. mp verify executor constraints
- Rejects `&&`, `;`, and newlines in AC verification fields.
- Each line in a verification field must be a self-contained command.
- `--skip-verify` is debt, not a shortcut. Use it only as last resort
  and document why in commit message.
- The future Drive milestone SHOULD fix the verifier to handle `&&`
  chains (split AC-06 verification into a single cargo nextest
  invocation that covers both crates — see M200 F-04 fix).

#### 9. Build-cleanliness discipline
- `make clean` before each review cycle that involves validation.
  Removes stale cargo artifacts that can mask source-level regressions.
- 28.8 GiB / 772k files took ~30s to clean in M201 cycle 3.
- Cold build after clean: ~10 min for raul + mp test binaries.
- Establish as a routine: every milestone cycle starts with a clean build.

#### 10. Per-AC evidence discipline
- Evidence must be a per-AC command + exit code + test count, NOT a
  generic string.
- Cycle 1 of M200 had `evidence: "All 5 reviewer findings (F-01..F-05)
  resolved. All 6 AC verifications + 8 step tests pass honestly
  without --skip-verify."` — useless for reproduction.
- Future skill template: per-AC evidence MUST include the actual
  command, exit code, and pass count.

#### 11. Reviewer contract
- Reviewer does NOT edit crates/. Writes limited to `mp reviews *`.
- Reviewer activation: by orchestrator prompt (not lifecycle gate).
  This avoids the M200 problem of the milestone being approved but
  not done, blocking the gate.
- Reviewer response: same notification contract as runner.

#### 12. TUI caveat (from M201 ID-01/ID-11 incident)
- `mp idea create --body @file` stores the body as a path reference
  (TUI doesn't render those — the idea is invisible in the TUI tab).
- Use `--body "$(cat file)"` for inline storage.
- Future: file as TUI bug.

#### 13. Lifecycle state model (M196)
- States: approved → in-progress → executed → complete (with
  remediation as a side-state from open findings).
- `mp milestone complete` → `executed` (terminal from executor side).
- `mp reviews pass --verdict ok` → `complete` (terminal).
- `executed` does NOT auto-promote to `complete`. The reviewer pass is
  required for the final transition.
- `lifecycle=executed` is the M196 terminal state, replacing the older
  `lifecycle=done`. Code that gates on `lifecycle=done` will break.

#### 14. herdr integration quirks
- `herdr pane read` defaults to `--source recent` which returns EMPTY.
  Always pass `--source visible` to see current screen.
- `herdr agent prompt --wait --until idle` matches the FIRST observed
  turn boundary after submission. Doesn't distinguish "did nothing"
  from "finished". For multi-turn, use `--until working` first.
- The opencode bridge never reports `agent_status=done` reliably
  (M149 review finding). Use `mp show milestone` lifecycle polling,
  NOT herdr agent status, for completion gating.
- `target/debug/mp` is the freshly built binary; `/opt/homebrew/bin/mp`
  is the installed (possibly stale) one. For source-level fixes,
  rebuild and use target/debug/mp or `make install` first.

#### 15. Log file fragility
- mp-herdr-log.txt at the repo root has been truncated multiple times
  during this test (cause unknown; not pursued).
- Substantive test state lives in git + plan.json + activity.json, not
  in this narrative log.
- The future Drive milestone should:
  (a) Move the orchestration log INTO master-plan/ as a structured
      record (probably under reviews/ or as a new orchestrator_log.json).
  (b) Use git commits to preserve history (commit log entries
      alongside milestones).
  (c) Surface log entries via `mp` commands so they're discoverable
      from the plan zone.

### What this test did NOT validate

(These are gaps in our knowledge for the future redesign.)

- **raul UX layer.** The whole test was opencode-driven, not raul-driven.
  The Drive milestone must build the "Drive" button + topology chooser
  + status view + pause/cancel/steer controls. No design work yet.
- **Planner lane.** The planner role was used briefly (M200 cycle 0)
  and dropped. We never tested spec-grill from a separate lane.
- **Concurrent milestones.** We drove M200, M201, M202 sequentially.
  No test of multiple milestones in parallel.
- **`mp watch` integration.** `mp watch M200` was never run. We
  hand-rolled the orchestration instead. The future milestone needs
  to actually USE `mp watch` (or its successor).
- **Failure recovery.** We didn't test pause/cancel/steer from raul.
- **Production binary path.** We used `target/debug/mp` after cycle 3
  of M201 because the installed binary was stale. Production needs
  to handle this cleanly.

### Migration plan: log → master-plan/

The current mp-herdr-log.txt is fragile. The future Drive milestone
should include:

1. Define an `orchestration_log.json` schema (or use reviews/challenges/<id>.json).
2. Every orchestrator event (cycle start/end, finding filed/resolved,
   state transition, decision made) gets an entry there.
3. The log is queryable via `mp orchestration log M200` (or similar).
4. The log is git-tracked so it survives truncations.

For NOW (until the future milestone lands):
- The current mp-herdr-log.txt is the best we have. It's incomplete
  (truncation events) but covers the major lessons.
- Keep appending after every meaningful cycle.
- If a milestone's lessons are critical, ALSO write them to
  master-plan/decisions.json or similar for durability.

## 2026-09-01 ~23:35 — consolidated lessons (the hard ones)

### Three lessons that recurred across all three milestones

#### Lesson 1: Lane notifications must be SHELL COMMANDS, not printed text
- M200 cycle 1: runner printed notification in TUI instead of running `herdr agent prompt`.
- M201 cycle 1: runner fabricated the lifecycle claim entirely.
- M202 cycle 1: 11 findings but with placeholders / generic strings.
- **Fix:** every lane prompt must show the exact shell command for the notification. The word "notify" is interpreted as "print" by opencode agents by default.

#### Lesson 2: Per-AC evidence discipline (THIRD REPEAT — load-bearing)
- M200 F-12 (cycle 2): "milestone completion" step overwrote evidence with generic string.
- M201 F-05 (cycle 1): evidence counts disagreed with actual test counts in 3 ACs.
- M202 F-13 (cycle 3): cycle-2 completion commit 10a5586 replaced all 19 AC evidence with placeholder "M202 cycle 2 retry".
- **Pattern:** any "summary" or "completion" step that touches milestone JSON tends to overwrite per-AC evidence. Three milestones, three occurrences.
- **Fix:** evidence restoration MUST happen AFTER any completion ceremony. Restoring evidence via `mp milestone criterion pass <AC> --evidence "..."` is the only safe path. NEVER have a completion-summary commit touch evidence fields. The future Drive milestone should codify this as a hard rule for the runner contract.

#### Lesson 3: Orchestrator must verify state independently
- M200: state was at `executed` but review-pass event was lost to a regression.
- M201 cycle 1: runner claimed "lifecycle=executed" but state was at approved/planned.
- **Fix:** before accepting any lane's "done" notification, the orchestrator MUST independently verify:
  ```
  state = mp show milestone <id> --fields milestone.lifecycle,milestone.execution_status
  acts  = grep '"subject": "<id>"' master-plan/activity.json | tail -3
  assert state.lifecycle in {executed, complete}
  assert state.execution_status == "done"
  assert len(acts) > 0
  if any check fails: REJECT and send back
  ```

## 2026-09-01 ~23:40 — OPEN DECISION: git commit strategy

The future "Drive milestone" / new mp watch needs an explicit git commit
strategy. The current test ran with whatever the runner chose per-cycle,
and that produced inconsistencies.

### What we observed

| Milestone | Steps | Findings | Commit pattern | Audit-trail consequence |
|---|---|---|---|---|
| M200 | 8 | 13 (over 4 cycles) | 1 commit per step group + 1 per cycle resolution + 1 lifecycle evidence commit | clean step history, but `fixed_in` got cross-stamped in cycle 1 (F-11 lesson) |
| M201 | 16 | 13 (over 3 cycles) | 1 commit per step group (5 commits for 16 steps) + 1 per finding (3 cycle-2 commits) + 1 lifecycle evidence | grouped-step commits made per-AC evidence restamping necessary in cycle 3 |
| M202 | 22 | 13 (over 3 cycles) | 1 commit per step group (9 commits for 22 steps) + 1 per finding (cycle 2: 4 commits for 11 findings, several grouped) + 1 lifecycle evidence | cycle 3 F-13: a "completion summary" commit overwrote all per-AC evidence with a placeholder string |

### Cross-cycle patterns

1. **Per-step commits** — the runner's natural unit. Some steps are
   trivial enough that they were bundled (S1-S3 in M201), others were
   kept as one commit per step (S4 in M201).
2. **Per-finding commits** — the reviewer expects `mp reviews finding
   resolve --commit <sha>` to point to the actual fixing commit.
   Grouped finding commits (M202 cycle 2: F-01..F-05 + F-08 + F-11 in one
   commit `eb3b66d`) made `fixed_in` resolve ambiguous — every finding
   got the same SHA.
3. **Lifecycle evidence commits** — at the end of each cycle, a commit
   that records the milestone's final state for that cycle.
4. **Resolve findings commits** — separate from the fix commits; just
   the `mp reviews finding resolve --commit <sha>` calls. Often grouped
   into one commit (M202 cycle 2: `cb2e0d9 resolve F-01..F-11`).

### What's broken about the current ad-hoc strategy

- **`fixed_in` metadata drift.** When findings are grouped into one
  commit, every finding gets that single SHA as `fixed_in`. The audit
  trail loses which finding was fixed in which commit. M200 F-11
  caught this: 5 findings all stamped `0f246fa`, but F-01 was actually
  fixed in `63266db`, F-02 in `98dd281`, etc.
- **Evidence overwrite by "completion" commits.** M200 F-12, M201 F-05,
  M202 F-13 all had a "milestone complete" or "cycle evidence" commit
  that overwrote per-AC evidence with a generic string. Any
  cycle-bounded summary commit touches evidence fields by accident.
- **Step granularity varies.** S1 alone in one commit, but S1-S3 in
  another commit. Inconsistent makes bisect harder.

### Open decision for the new mp watch / Drive milestone

The Drive milestone MUST pick a strategy. Options:

**A. One commit per step (strict)**
- Pros: clean audit trail, easy step-level revert, predictable.
- Cons: lots of commits (22 for M202). `fixed_in` is unambiguous when
  finding fixes coincide with step work. Tedious for trivial steps.

**B. One commit per finding (strict)**
- Pros: `fixed_in` is unambiguous. Easy to track what fix landed where.
- Cons: doesn't capture step-level progress. Implementation commits
  don't fit this model.

**C. One commit per AC pass (strict)**
- Pros: ties commits to acceptance criteria. Ties to the AC verification.
- Cons: steps cover multiple ACs; one AC may pass without a clean commit
  boundary. Awkward granularity.

**D. One commit per cycle (end-of-cycle)**
- Pros: cycle-bounded rollback. Single commit shows the cycle's net
  change.
- Cons: loses step-level and finding-level granularity. Hard to
  bisect within a cycle. Audit trail collapses.

**E. One commit per milestone (end-of-milestone, single squashed commit)**
- Pros: clean "this milestone did X" semantic. Bisects milestones, not
  steps.
- Cons: bisecting within a milestone is impossible. Hard to revert a
  single cycle's findings. Loses finding-level audit trail entirely.

**F. Hybrid: per-step implementation commits + per-finding fix commits + lifecycle-evidence meta-commit (current, informal)**
- Pros: flexible, matches what reviewers expect.
- Cons: ad-hoc, inconsistent across runs, produced the evidence-overwrite
  + fixed_in-drift issues we saw.

### Recommended strategy (proposed, not yet decided)

A **strict four-tier commit policy** for the new watch system:

1. **Per-step implementation commits.** One commit per step during the
   runner's initial execution. Trivial steps may be grouped with the
   next step (but document the grouping in the commit message:
   `M<id>: S<step> + S<step+1> — both touch <feature>`).

2. **Per-finding fix commits.** One commit per finding during
   remediation cycles. NEVER group multiple findings in one commit
   (this is what broke `fixed_in` metadata in M200 and M202).

3. **Lifecycle evidence meta-commit.** One separate commit at the end
   of each cycle with NO code changes — just records the milestone
   state for that cycle. Must NOT touch `acceptance_criteria[].evidence`
   fields (those are set by per-AC pass, see #4).

4. **Per-AC evidence restoration.** Each AC's evidence is recorded
   via `mp milestone criterion pass <AC> --evidence "..."` which writes
   directly to the milestone JSON. NEVER overwrite via a generic
   "summary" commit.

5. **Resolve findings commit.** One `mp reviews finding resolve --commit <sha>`
   per finding, grouped into a single commit per cycle. The `--commit`
   argument for each finding points to the actual fix commit (#2),
   NOT to the resolve commit (#5).

### What the Drive milestone must enforce

The runner contract for the new watch system should specify:
- A `commit_strategy` field or similar, defaulting to the recommended
  four-tier policy.
- A pre-commit hook (or pre-push hook) that warns when a commit
  touches both code AND `acceptance_criteria[].evidence` fields.
- A `mp reviews finding resolve` validation that checks the `--commit`
  SHA actually contains the fix (e.g., `git log --oneline <sha>^-1..<sha>`
  mentions the finding ID).

### Test this in the future Drive milestone

A future re-run of this test (M200/M201/M202 with the strict
four-tier policy) should verify:
- Per-step commits are 1:1 with the spec (or documented grouping).
- Per-finding commits are 1:1 with the reviewer's findings list.
- Lifecycle-evidence commits don't touch evidence fields.
- `fixed_in` resolves to the actual fix commit, not the resolve commit.

## 2026-09-01 ~23:50 — OPEN DECISION: milestone document structure

The future "Drive milestone" / new mp watch should rework milestone

### Current state (fragmented)

A single milestone's information is split across 4+ files:

|---|---|---|

| Findings (from reviews) | `master-plan/reviews.json` (global) | Hard — must filter by subject |

| Backlog items sourced from this milestone | `master-plan/backlog.json` (global) | Hard — must filter by source |
| Decision references | `master-plan/decisions.json` (global) | Hard — must filter by milestone |

For a milestone like M200, the agent has to grep 3+ files to find
everything related to it. There's no single "place" to look.

### User's requirement

> "Keep all milestone information we could in a single 'place' — be it
> a folder or a file. Like, aside the milestone itself, keep at the
> same place the result of the rounds of code review, add comments
> about the runner describing the execution, reporting issues or other
> difficulties. And any other possible information like the status
> and some log when the lifecycle changed. This kind of metadata
> about the milestone."

### Three options

**Option A: Per-milestone folder (multiple JSONs, one folder per milestone)**

```
master-plan/
  milestones/
    M200-keybind-deconflict/
      spec.json              # the milestone spec (currently in milestones/200-*.json)
      findings.json          # all findings for this milestone (F-01..F-13)
      runner_notes.json      # runner's commentary: what was hard, workarounds, surprises
      lifecycle.json         # lifecycle transitions for this milestone
      challenges.json        # challenge sessions (if any)
      dependencies.json      # what blocks this milestone (planned)
      backlog.json           # backlog items sourced from this milestone
      decisions.json         # decision references for this milestone
      reviews.json           # per-cycle review summaries (one entry per cycle)
```

- Pros:
  - All milestone metadata in one discoverable place.
  - One folder = one milestone. Easy to grep, copy, archive.
  - Scales — adding a milestone adds a folder, not a new global file.
  - Each file can be read/written independently (no merge conflicts on
    unrelated fields).
  - Backward-compatible transition: keep old `milestones/<id>-*.json`
    files as `spec.json` until migration is complete.
- Cons:
  - More files (4-7 per milestone vs 1 today).
  - `mp` CLI needs updates to know about the folder structure.

**Option B: Single global JSON with all milestones**

```
master-plan/
  milestones.json   # everything for all milestones
```

- Pros:
  - Simplest. One file to read.
  - Easy to query the whole plan at once.
- Cons:
  - File grows unboundedly (one entry per milestone × all metadata).
  - Concurrent writes serialize behind one file lock.
  - Hard to archive a single milestone (extract subtree).
  - Hard to bisect "what changed for M200" in git (diff is huge).
  - Single point of failure — corrupt one entry, lose everything.
  - **REJECTED** based on the user's "single place PER MILESTONE" framing.

**Option C: Extend current single file per milestone with embedded arrays**

```
master-plan/
  milestones/
    200-keybind-deconflict.json   # contains spec + findings + lifecycle + notes + ...
```

- Pros:
  - Minimal structural change. Backward compatible.
  - Single file per milestone.
- Cons:
  - File gets huge for milestones with many findings/cycles (M200 has
    13 findings + 8 lifecycle entries + would-be runner notes = potentially
    30+ entries in one JSON).
  - Concurrent updates to different fields still serialize.
  - Hard to read; the milestone spec is buried under metadata.

### Recommended: Option A (per-milestone folder)

The user explicitly said "a folder OR a file" — they're open to a folder.
Option A is the most scalable, the most readable, and the most git-friendly
(milestone-scoped diffs become natural).

### Migration plan

The transition from current structure to folder-per-milestone should
happen in three phases:

1. **Phase 1: Add folder support alongside current files.**
   - `mp` reads either `<id>-*.json` OR `<id>/spec.json`.
   - New writes go to `<id>/spec.json`.
   - Backward-compatible: old files still work.

2. **Phase 2: Migrate findings + lifecycle.**
   - For each existing milestone, copy findings from `reviews.json`
     into `<id>/findings.json`.
   - Copy lifecycle transitions from `activity.json` into
     `<id>/lifecycle.json`.
   - `reviews.json` becomes a global index (subject + finding count + link to per-milestone files).
   - `activity.json` becomes a global event log (less per-milestone state).

3. **Phase 3: Deprecate old structure.**
   - `reviews.json` is now just an index.
   - `activity.json` is now just an event log (lifecycle transitions
     may still go here OR migrate per-milestone).
   - Per-milestone folders are the source of truth.

### What this enables

- **One-grep discovery** for any milestone's metadata.
- **Per-milestone git diffs** — easier to review and bisect.
- **Per-milestone archival** — close out a milestone by moving its
  folder to `master-plan/archive/milestones/<id>/`.
- **Runner notes preserved** — currently lost when the runner's
  context window rolls over.
- **Future Drive milestone** can use `runner_notes.json` to
  surface WHY decisions were made, not just WHAT happened.

### What the Drive milestone must enforce

- The runner's contract should require `runner_notes.json` entries for:
  - Workarounds (any deviation from the spec)
  - Surprises (anything that violated expectations)
  - Blockers (anything that prevented completing a step)
  - Decisions (any judgment call that wasn't in the spec)
- The reviewer can append to `runner_notes.json` too (e.g., "this finding
  is high because the spec is misleading").
- The orchestrator reads `runner_notes.json` after each cycle to inform
  cycle-count decisions (e.g., a note "this is the third time this
  regex broke" might trigger escalation).

1. **opencode permission config** — the hardest backstop. `mp reviews pass` is
   in the runner's DENY list. Even if the prompt fails, the shell call is rejected.
2. **Skill file content** — the contract. Each skill has a "What you CANNOT do"
   section that the agent reads before acting.
3. **Prompt reinforcement** — the per-cycle prompt echoes the key boundaries
   (`DO NOT call mp reviews pass`). Already tried and failed for M203 (the
   runner went beyond the prompt). Useful as a third layer but not enough alone.
4. **Orchestrator verification** — after the lane notifies, the orchestrator
   checks activity.json for a `mp reviews pass` event when lifecycle=complete.
   If absent, REJECT and send back.

### Why this matters

M203 was the second reminder (after M200's "lifecycle=executed" fabrication)
that the runner agent can deviate from intent. The runner does what it
understands the goal to be. If the goal is "complete the milestone",
the runner will complete it — by any means available, including
violating role boundaries. The fix isn't to ask the runner more nicely;
the fix is to make the boundary mechanically enforced.
