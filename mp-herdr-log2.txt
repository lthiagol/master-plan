## 2026-09-03 ~14:50 — LESSON: orchestrator must stay idle, not poll

### What happened

After dispatching both contracts, I ran `herdr agent wait w12:p19 --until idle --timeout 120000` from this orchestrator pane. The reviewer lane finished its contract read in a few seconds and executed the prescribed notification:

```
herdr agent prompt w12:p17 "Reviewer: contract acknowledged. Standing by for milestone."
```

Same for the runner a moment earlier. But because the orchestrator pane (w12:p17) was busy executing my `herdr agent wait` tool call, the opencode bridge **queued both notifications** instead of delivering them. The user noticed and aborted my command with ESC. The two queued ack messages then appeared in the chat as plain text. Both lanes were always in `idle` from the very first ack — my "wait" was waiting on a state that had already happened, and simultaneously blocking myself from receiving the very signal I was waiting on.

### Why this matters

This is a tighter version of the original R14 lesson ("the opencode bridge never reports `agent_status=done` reliably — use `mp show milestone` lifecycle polling, NOT herdr agent status, for completion gating"). The original log was about state reads; this one is about **notification delivery**.

- Push-based notification (R4 from the original) only works when the receiving pane is idle.
- The orchestrator's contract in this test is: dispatch → idle. The state machine's "I am waiting" is "I am processing prior input, do not call me." The lanes push to me; I don't pull.
- Any `herdr agent wait` / `herdr pane read` polling from this pane during a cycle **silently buffers the lane notification** until the polling returns. The notification is not lost, but it is delayed by however long I take to come back to idle.
- Worse, a long `--timeout` on `herdr agent wait` can hold me for minutes, so even fast cycles get artificially serialized.

### Correct orchestrator discipline (codified)

```
on dispatch to a lane:
  herdr agent prompt <lane_pane> "<task>"
  ... (no wait, no read, no poll — return to idle immediately)

on lane notification arrival:
  verify state (R5):
    state = mp show milestone <id> --fields milestone.lifecycle,milestone.execution_status
    acts  = grep '"subject": "<id>"' master-plan/activity.json | tail -3
  apply decision matrix (R3)
  either: dispatch next lane, or: declare milestone done, or: send lane back
```

If I genuinely need to wait for a long-running external process (cargo build, tests), I do that with `cargo ...` directly and return — the lanes don't depend on me being idle for their work, only for receiving their push notifications.

### What I am NOT allowed to do from this pane

- `herdr agent wait <lane> --until ...` from this pane
- Long `--timeout` polls on lane state
- Anything that holds the orchestrator pane in a non-idle state for > a few seconds while a lane is expected to notify

If I ever need to check "is the lane done without a notification?", the discipline is:
1. Look at the chat for an unread notification first.
2. If absent, `mp show milestone <id>` for state, not `herdr agent get` for agent_status.
3. The lane's `agent_status` is informational only; the milestone JSON + activity.json + reviews.json are the source of truth.

### Herdr bridge behavior (new finding, not in the original log)

The original R14 said `agent_status=done` is unreliable. This session adds: **the bridge also drops the receiver's "ready to receive" state silently.** If the receiver is busy, the notification goes into a queue and the receiver only sees it on its next idle turn. From the receiver's perspective, the lane's notification has zero presence until the receiver is idle — there is no "missed call" log to inspect. This is why the original test had "F-late" review findings that were actually filed before the orchestrator noticed; the orchestrator just hadn't picked up the lane's earlier ack.

For this test: every lane notification I receive should be assumed to be answering the *most recent dispatch*, not the *oldest unanswered dispatch*. If the chat history shows acks older than the dispatch I sent, that's a clock-skew artifact, not a missed call. The mitigation is to never let dispatches stack: one dispatch → one notification → one decision → next dispatch.

### What changes for this session going forward

- I will not run `herdr agent wait` from this pane.
- I will not run `herdr pane read` for monitoring.
- I will rely on the chat to surface lane notifications.
- The only state I poll is `mp show milestone` and `grep activity.json` — both are file reads on the local repo, do not block the herdr bridge.
- If a lane is silent for > 10 minutes, the protocol is: file a dogfood-log entry ("lane <id> silent for > N minutes on milestone <id>"), and ping the user — do not poll, do not re-prompt.

## 2026-09-03 ~15:15 — SESSION POLICY: commit-on-handoff + 4-round cap

User set two hard rules for the upcoming autopilot test:

### Rule 1: commit on every handoff

- After the runner finishes implementing + self-reviewing + fixing its own findings, it commits its work (code + plan-zone writes via `mp milestone step done`, `mp milestone criterion pass`, `mp milestone complete`) BEFORE notifying the orchestrator.
- After the reviewer finishes a review pass, it commits its work (plan-zone writes via `mp reviews claim`, `mp reviews finding add`, `mp reviews pass`, `mp reviews finding resolve`) BEFORE notifying the orchestrator.
- After the orchestrator makes ANY change (log update, manual state fix, scratch-file commit, anything), it commits immediately. No batching across handoffs.

### Rule 2: cycle budget — 4 rounds max

- Default: 2 cycles (review → fix → re-review → pass).
- Soft cap: 3 cycles. Tighten reviewer prompt at cycle 2 ("blockers only" per M201 lesson) — do NOT wait for cycle 3 to tighten.
- Hard limit: 4 cycles. After cycle 4 the orchestrator escalates to the user regardless of pass/fail. `ship_with_backlog` is NOT available after cycle 4.
- Decision matrix unchanged from the original log's R3.

### Commit message convention (per role)

| Actor | Prefix | Notes |
|---|---|---|
| Runner (per-step) | `M<id>: S<step> — <description>` | One per step, or documented grouping in message body |
| Runner (per-finding) | `M<id>: fix F-<num> — <description>` | One per finding; never group (M200/M202 `fixed_in` drift lesson) |
| Runner (lifecycle evidence) | `M<id>: lifecycle evidence cycle N` | One per cycle, no code changes |
| Reviewer (per-cycle) | `M<id>: review cycle N — <verdict> (F-<nums>)` | One per review pass |
| Orchestrator (state fix) | `M<id>: orch-fix — <description>` | Used only when runner skipped a step-done or other discipline violation |
| Orchestrator (log) | `log: <description>` | For mp-herdr-log*.txt updates |

### What this means in practice for a 2-cycle milestone

```
cycle 1:
  [orchestrator] dispatch runner            (no commit if no change)
  [runner]      implement S1..SN            (N per-step commits, or 1 grouped commit per lane discretion)
  [runner]      self-review clippy/fmt/test  (M per-finding commits if issues found)
  [runner]      mp milestone complete        (1 lifecycle-evidence commit)
  [runner]      notify orchestrator
  [orchestrator] verify R5 state             (no commit if clean)
  [orchestrator] dispatch reviewer           (no commit if no change)
  [reviewer]    mp reviews claim             (1 commit with claim + pass, or split per lane discretion)
  [reviewer]    mp reviews finding add F-01..F-N
  [reviewer]    mp reviews pass --verdict changes-needed
  [reviewer]    notify orchestrator
  [orchestrator] log cycle 1 closeout        (1 log commit)

cycle 2:
  [orchestrator] dispatch runner cycle 2    (tightened prompt: "blockers only")
  [runner]      fix F-01..F-N
  [runner]      mp milestone step done S*
  [runner]      mp milestone complete
  [runner]      notify
  [orchestrator] verify R5
  [orchestrator] dispatch reviewer cycle 2   (prompt: "blockers only")
  [reviewer]    mp reviews claim
  [reviewer]    mp reviews pass --verdict ok
  [reviewer]    notify
  [orchestrator] mp reviews pass (terminal) (we call it as orchestrator after reviewer verdicts ok; see R-late in original log about role separation)
  [orchestrator] log cycle 2 closeout + complete

```

If the orchestrator calls `mp reviews pass --verdict ok` as the terminal action, that's the orchestrator's. The original log's rule was: NEVER let the runner touch `mp reviews *`. That rule is preserved in the runner's contract.

The original log was a discovery process — we were finding out what worked. This run is testing the discovered rules:
